Ideas and gaps found during work, not yet nodes. Triage with the user.

- 2026-10-30, from the selfhost-check-imports review (#34): `narrac decls` is quadratic in the number of declarations in one module (2000: 0.3 s, 4000: 1.15 s, 8000: 4.9 s); main shows the same, so it predates #34. Not located; likely the declaration passes or the dump. Fix before the selfhost compiler checks large generated files.
- 2026-10-30, same review: `TestSelfhostBuiltins` checks fixed-signature builtins with a one-way compile probe, so a Go parameter widened beyond the Narra table, or a result that is a subtype, passes. A Go-side dump of `checkFixed` signatures would make it exact.
- 2026-11-01, from the std-iterator discussion: async generators (`async function*`, "not in the first version" in SPEC section 8) would let `std/iterator` operators work on async streams, like IxJS AsyncIterable. Add time operators (`debounce`, `throttle`, `merge`) to `std/async` with them. Needs async and generators first.
- 2026-11-01, user direction: make closures more powerful and closer to TypeScript semantics after m11-closures. Candidates to weigh: inferring `escaping` where the cost is still visible in tooling, capturing `let` from escaping closures through an automatic `Cell`, and async closures. Each needs a decision record; run a goal debate before planning.
- 2026-11-02: compound assignment (`+=`, `-=` and the rest), increment and decrement (`++`, `--`), user request. Added as outline node compound-assign.
- 2026-11-05, from refining std-io-more: Path.basename suffix form (Node's basename(path, ext)) or a stem helper, if callers need it.
- 2026-11-05, from the PR #82 review: outside a parameter list, a `uses` list on a type takes every following `, name` as another effect (`parseUsesList`). So `#[Generator<int> uses io, int]` and `Map<Generator<int> uses io, int>` parse as one generator with effects `io, int`, and `#[Generator<int> uses io, Array<int>]` is a parse error. A trailing comma after `... uses E` in a parameter list gives `expected a name, found ")"`. Function types with `uses` have the same problem. A type with `uses` can only come last in a type list. Needs a language decision (for example parentheses around the effect list, or effects only after a name that is a known effect).
- 2026-11-05, from reformatting the sources (chore/fmt-sources): `narrac fmt` does not hug a block expression in the last call argument. `addAll(mutable xs, { ... })` becomes one argument per line with the block on its own line, where oxfmt keeps a last-argument function or object on the call line. A block as a binary operand (`x + { return f() }`) breaks into `x +` and an indented block on the next lines. See `compiler/testdata/errors/block_expressions_mutable_arg.nra` and `mutable_read_conflict_block_operand.nra`.
- 2026-11-05, from the PR #88 review (query-cli): the parser gives every token inside a template literal's `${...}` the template's start position (`selfhost/src/parser.nra`, about line 2255). Diagnostics and `narra query` locations inside templates point at the backtick; query works around it (`inTemplate`). Fix in the parser with real positions, then update the AST dump goldens and drop the query workaround.
- 2026-11-05, from the PR #89 review (generators), a bug on main from generators-check: a `function*` cannot be assigned to a variable with a function-type annotation. `const g: (x: int) => Generator<int> = count` fails with "expected (int) => Generator<int>, found (int) => Generator<int>"; an unannotated `const f = count` works. Needs its own fix PR (likely a type identity mismatch between the generator's function type and the annotated one).
- 2026-11-05, from writing guide chapters 6 to 10: two misleading compiler hints. (1) Assigning to a field of a parameter says "declare it with `let`"; for a parameter the fix is `mutable` or returning a new value. (2) A missing `implement` block for a user trait suggests `derives Label`, but user traits cannot be derived. Both affect the guide's error samples (chapters 7 and 9).
- 2026-11-05, from the review of PR #87: `TestGuide` skips `narra fragment` blocks, so multi-file package samples are not compiled (a chapter 4 fragment that did not compile slipped through). Add a multi-file sample form to `contracts/guide-samples.md` (for example a named package with several fragments that the test assembles and builds), then convert the chapter 1, 4 and 8 package samples.
- 2026-11-05, from the PR #88 round-2 review, an effect soundness bug on main in both checkers: a call through a function-typed struct field or through a call's result does not contribute its declared effects. `export struct Box { run: (value: string) => int uses alloc }` and `export function pure(box: Box): int { return box.run("x") }` check clean; a direct `Str.join(...)` in the same body is correctly rejected. Needs its own fix PR (both checkers, plus error tests); `narra query` reports `effects: []` on such calls until then.
- 2026-11-07, from the review of PR #96: (1) SPEC.md section 2 still says "There are no compound assignments (`+=`, `++`)", while D76 (2026-11-04) decided to add them; update SPEC when nodes c-style-for and compound-assign land, or now with a "not built yet" line in `compiler/README.md`. (2) Arguments are not evaluated left to right: with `let items = ["a", "b", "c"]`, `show(items, { items = ["z"]; return 0 })` prints 1, not 3, because the block argument runs before the earlier argument is read. Needs a fix in both emitters (evaluate earlier arguments into temporaries when a later argument has side effects), or a SPEC rule and a check that rejects it.
- 2026-11-07, user idea, feasibility open: named arguments at the call site, `foo(a = 1, b = 2, c = 3)`. Questions for a goal debate: (1) SPEC line 41 says syntax follows TypeScript where the meaning is the same, and in TypeScript `foo(a = 1)` assigns to `a` and passes the result. Narra assignment is a statement, so the parse is free, but a TypeScript reader would misread it; `foo(a: 1)` or `foo({ a: 1 })`-like forms avoid that, and `name:` already labels loops inside `{`. (2) Parameter names would become part of a function's public interface: renaming a parameter breaks callers, and function types (`(item: T) => U`) would need to keep or drop names. (3) SPEC section 2 has no optional parameters and points to a struct with defaults (`File.open(path, OpenOptions { create: true })`); named arguments overlap with that, and add value mostly if defaults on parameters come with them. (4) Mixed positional and named arguments, order rules, and evaluation order (see the left-to-right entry above).
- 2026-11-07, user idea, next syntax feature after the current wave: async blocks and generator blocks, block expressions (D75) that suspend. Open questions for a goal debate before planning: (1) What value each block has. A generator block could be a `Generator<T>` value (`const evens = function* { ... }`-like, syntax to pick); an async block has no `Promise<T>` to become (SPEC section 8 has only `Task<T>` from `Async.spawn`), so it is either sugar for `async () => { ... }` or a new awaitable type. (2) Generators are top-level only and have no arrow form (D74, SPEC section 8); a generator block captures locals, so it needs the escaping-closure capture rules (constants only, E0612/E0613) and a heap frame, or a non-escaping form tied to `for ... of` in the same scope. (3) `return` inside a block expression ends the block (D75); in a generator block it would end the generator, and in an async block it gives the result. (4) Effects: the block's type carries the body's effects (D78). (5) Both state-machine transforms (generators, async) run on whole functions today; blocks need them on a nested body with captures. Depends on the closure work in the 2026-11-01 entry (async closures) and on async generators if both kinds combine.
