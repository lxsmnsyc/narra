# Log: std-async-io

- 2026-11-13: branch renamed to feat/std-async-io, reset to feat/batch-12 (8663a897). event-loop built `std/async/time` and `narra_loop_wait_io`; nothing of net or file existed.
- Handle: `Type.THandle`, named `Handle` only in modules that import `std/internal/asyncio` (scopes.nra, as `StringBuilder` for std/string). Counted (`isCountedType`), not a contents type, not copy tracked, no Equatable or Hashable. C type `narra_handle*`; retain and release note the `std/internal/asyncio` helper.
- Runtime `std_async_io.c` needs nothing from the task runtime: `Handles.wait` and `Handles.cancelled` emit `narra_loop_wait_io(...)` and `narra_loop_cancelled_now()` into the program, which comes after every runtime part, so the order of `checker.used` does not matter.
- Errors: each primitive stores errno in a `_Thread_local narra_io_error`; `Handles.error()` reads it right after the call, before any await, so no other task can overwrite it. A failed `listen`, `connect` or `accept` gives a handle with descriptor -1, which never reaches a `Listener` or `Connection`.
- First try put the wait in a helper `async function waitFor`: a cancel would not reach it, since `forwards_cancel` is set on the helper's task and not on the task of `read` that the user awaits. Each suspending function awaits `Handles.wait` itself; `checkWait` is a plain function over the wait's value.
- SIGPIPE: `send(..., MSG_NOSIGNAL)`, available on macOS 15 under `_POSIX_C_SOURCE` and on Linux. A write to a closed peer is an `EPIPE` error.
- File calls: check `Handles.cancelled()` first (no file touched), do the `std/fs` call, then `await Tasks.sleep(0)` for one turn of the ready tasks. A task started by a cancelled user task is not cancelled itself (event-loop rule), so the sample calls `AsyncFile.writeText` straight from the cancelled block.
- spec suite: its wrapper added a second `run` when the sample's entry is `export async function run(`; `selfhost/tests/src/spec.nra` now looks for both forms.
- Review round 1 (2026-11-13): accept retries the per-connection errors of accept(2); read uses a 64 KiB buffer and returns only what came, and gives empty bytes for maxBytes <= 0; EEXIST from a second waiter maps to "another task is already ..."; listen uses SOMAXCONN.
- Maintainer ruling: a cancel passes down the await chain to a task whose only waiter is the cancelled task. Built in `narra_loop_cancel_wait`, and `narra_task_wait` passes the cancel of an already-cancelled task when it suspends. Proof: with the old runtime text, `async_io_cancel_chain` hangs (killed by an 8 s alarm, no output).
